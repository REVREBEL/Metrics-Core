# StayInTouch PMS Source

This page is the maintained source-specific reference for StayInTouch PMS data used by Metrics. It documents the raw report pair, CRS enrichment file, five-step processing pipeline, standardized BigQuery output, and source behaviors discovered while validating rooms, revenue, reservations, pace, and STLY reporting.

Everything documented here applies to the **StayInTouch PMS** source unless another source is explicitly named. Repository code and current warehouse definitions remain the implementation source of truth.

| Attribute | Current value |

## Step 01: merge StayInTouch reports

The pipeline searches for the latest files matching `_RESV_Export` and `_STAY_Export`. It detects the real CSV header using anchor text rather than assuming a fixed row number. Current anchors include labels such as `Reservation Id`, `Hotel Code`, `Arrival Date`, `Lead Days`, and `Nights`.

The reservation export contributes selected reservation-level attributes when available, including arrival and departure dates, arrival rate code, departure room type, cancellation date, booking timestamp, first and last night rates, lead days, nights, origin code, postal code, purpose of stay, and state.

The reservation subset is left-joined to the stay report using:

```text
Reservation Id + Hotel Code
```

The merged output receives `PROPERTY_CODE` and `SNAP_DATE`, parsed from the source filename.

## Step 02: CRS enrichment

The CRS file is matched to PMS data after identifiers are cleaned and values such as `.0`, blanks, `nan`, `none`, and `null` are removed.

| PMS side | CRS side |
| --- | --- |
| `Confirmation Number` or `confirmation_number` | `PMS_Confirm_Code` or `pms_conf` |

The CRS enrichment contributes fields such as:

| CRS source field | Processed field |
| --- | --- |
| `Confirm_No` | `crs_confirm_no` |
| `Channel_Connect_Confirm_NO` | `channel_confirm_no` |

Unmatched enrichment values are filled with `Unknown`. Merge quality should be monitored by tracking matched confirmation numbers and unknown CRS attributes.

## Grain and metric behavior

The base table is primarily a **reservation stay-date table**. A multi-night reservation normally appears once for each stay date. Room nights and nightly room revenue are additive after duplicate source rows are resolved, but reservation counts require intentional deduplication.

Use:

```sql
COUNT(DISTINCT confirmation_number)
```

at the intended reporting grain. A reservation may appear under multiple segments or room types when attributes change across stay dates, so dimensional reservation counts may overlap even when property-level totals are correct.

Use `rms_otb` for room production and `rev_otb` for current OTB or final room revenue. ADR should normally be calculated as:

```sql
SAFE_DIVIDE(SUM(rev_otb), SUM(rms_otb))
```

## Status and cancellation behavior

Known status variants include `CANCELED`, `CANCELLED`, `Cancel`, `NOSHOW`, `NO SHOW`, `CHECKEDOUT`, `CHECKEDIN`, and `RESERVED`. Normalize status values with trimming and uppercase before filtering.

When a reservation is canceled, StayInTouch retains the stay-date rows but changes current production to:

```text
rms_otb = 0
rev_otb = 0
```

Retained fields such as `stay_date`, `confirmation_number`, `rate`, `original_rate`, `arrival_date`, `departure_date`, `cancel_date`, `book_date`, `nights`, and `lead_days` support historical reconstruction.

## Reconstructing STLY OTB without a stored snapshot

A reservation existed at a historical snapshot when:

```sql
book_date <= as_of_date
AND (
  cancel_date IS NULL
  OR cancel_date > as_of_date
)
```

For rows that later canceled and now have zero production:

1. restore one room night for each eligible stay-date row;
2. restore only when the current status is canceled and `cancel_date > as_of_date`;
3. do not restore zero rows with no cancellation date;
4. reconstruct room revenue from the lower valid positive value of `rate` and `original_rate`.

Recommended guarded rate expression:

```sql
CASE
  WHEN rate > 0 AND original_rate > 0
    THEN LEAST(rate, original_rate)
  WHEN rate > 0 AND (original_rate IS NULL OR original_rate <= 0)
    THEN rate
  WHEN original_rate > 0 AND (rate IS NULL OR rate <= 0)
    THEN original_rate
  ELSE NULL
END
```

When neither retained rate is positive, the room night may still be reconstructed but revenue should remain unavailable and be tracked with a missing-rate diagnostic rather than silently treated as a valid zero-rate night.

This method is not identical to a true immutable daily snapshot when later rate, stay-date, room-type, segment, or partial-cancellation changes cannot be recovered. Future ingestion should preserve immutable daily snapshots or effective-dated reservation history.

## Snapshot and comparison rules

For STLY comparisons:

- TY uses the requested `snap_date`.
- STLY uses `DATE_SUB(snap_date, INTERVAL 1 YEAR)`.
- Closed months use final actual production.
- The current month is `ACTUAL_OTB`.
- Future months are `OTB`.
- Full-year rows combine closed actual months with current and future OTB.

The reporting window currently follows:

| Snapshot date | Report years shown |
| --- | --- |
| January 1 through September 30 | Current calendar year only |
| October 1 through December 31 | Current year plus following year |
| January 1 of the new year | Prior year drops; new current year only |

## Date and duration fields

Use source dates directly when possible:

```sql
lead_days = DATE_DIFF(arrival_date, book_date, DAY)
nights    = DATE_DIFF(departure_date, arrival_date, DAY)
```

`unique_lead_days` and `unique_nights` may be populated only on selected reservation rows and should not be summed across stay-date grain.

## Deduplication guidance

`MAX(rms_otb)` and `MAX(rev_otb)` may suppress duplicated stay-night rows, but are safe only when repeated rows represent the same economic record. Validate whether duplicates represent copied rows, multiple rooms, separate revenue components, or changing dimension assignments.

A candidate duplicate key is:

```text
confirmation_number
stay_date
roomtype
metric code only when preserving a changing dimension
```

Do not add changing dimensions to property-total deduplication unless preserving multiple assignments is intentional.

The pipeline contains a standing January 2026 success criterion:

| Filter | Expected value |
| --- | ---: |
| Stay dates | January 1–31, 2026 |
| Status | `CHECKEDOUT` |
| `SUM(rms_otb)` | 2,235 |
| `SUM(rev_otb)` | 175,872 |

Additional controls should compare row counts and production totals after each step, report unmatched PMS-to-CRS reservations, identify duplicate stay-night keys, track unassigned reporting dimensions, and compare reconstructed STLY results against any retained RMS snapshot extract.

## Known implementation notes

- Pipeline modules exchange files through `data_upload`, `data_processed`, `data_export`, and `data_failed` folders in Google Drive.
- Source files move to `data_processed` only after successful processing.
- Header detection should remain anchor-based rather than fixed-row based.
- Step 03 depends on the shared `REVREBEL/Metrics-Dataform` column standardizer.
- Step 04 currently reads operational mapping tables from Google Sheets.
- Step 05 is the final pipeline stage and owns BigQuery upload.
- There is no separate Step 06 in the current pipeline.
- `Unassigned` is a valid reporting bucket and must remain in totals.
- Total rows must be calculated from the underlying population rather than by adding overlapping dimensional reservation counts.
