# StayInTouch PMS Source

This page is the source-of-truth reference for the StayInTouch PMS data currently loaded into Metrics. It documents the raw report pair, the CRS enrichment file, the six-step processing pipeline, the standardized BigQuery output, and the source behaviors discovered while validating rooms, revenue, reservations, pace, and STLY reporting.

Everything documented here applies to the **StayInTouch PMS** source unless another source is explicitly named.

## Step 01: merge StayInTouch reports

The pipeline searches for the latest files matching `_RESV_Export` and `_STAY_Export`. It detects the real CSV header using anchor text rather than assuming a fixed row number. Current anchors include labels such as `Reservation Id`, `Hotel Code`, `Arrival Date`, `Lead Days`, and `Nights`.

The reservation export contributes these selected attributes when available:

```text
Reservation Id
Hotel Code
Arrival Date
Departure Date
Arrival Rate Code
Departure Room Type
Cancel Date
Created At Hz
First Night Price
Last Night Price
Lead Days
Nights
Origin Code
Postal Code
Purpose Of Stay
State
```

The reservation subset is left-joined to the stay report using:

```text
Reservation Id + Hotel Code
```

The merged output also receives:

```text
PROPERTY_CODE
SNAP_DATE
```

`PROPERTY_CODE` and `SNAP_DATE` are parsed from the source filename. The preferred naming pattern is `YYYYMMDD_PROPERTY_*`; the parser also supports a date near the end of an export filename.

## Step 02: CRS enrichment

The CRS file is matched to the PMS data after cleaning identifiers and removing values such as `.0`, blanks, `nan`, `none`, and `null`.

| PMS side | CRS side |
| --- | --- |
| `Confirmation Number` or `confirmation_number` | `PMS_Confirm_Code` or `pms_conf` |

The CRS enrichment currently contributes:

| CRS source field | Processed field |
| --- | --- |
| `Confirm_No` | `crs_confirm_no` |
| `Channel_Connect_Confirm_NO` | `channel_confirm_no` |
| `Channel_Cd` | `crs_channel_code` |

## Grain and metric behavior

### Stay-date grain

The base table is primarily a **reservation stay-date table**. A multi-night reservation normally appears once for each stay date. This makes room nights and nightly revenue additive across stay dates, but reservation counts require deliberate deduplication.

### Room nights

Use `rms_otb` for production room nights. Room nights are additive at stay-date grain after duplicate source rows have been resolved.

Do not calculate room nights by counting rows unless the specific query has confirmed that every included row represents exactly one room night and contains no duplicate records.

### Revenue

Use `rev_otb` for current OTB or final production room revenue. Other revenue categories remain separate:

```text
addon_revenue
fb_revenue
other_revenue
tax_revenue
fee_revenue
total_revenue
```

ADR should normally be calculated as:

```sql
SAFE_DIVIDE(SUM(rev_otb), SUM(rms_otb))
```

### Reservations

A reservation count is not additive across every dimension. Use `COUNT(DISTINCT confirmation_number)` at the intended reporting grain.

A reservation can appear under more than one segment or room type when stay-date rows changed during the reservation. Three July 2026 confirmations were confirmed to have multiple segment assignments:

| Confirmation | Stay-date segment behavior |
| --- | --- |
| `134371` | Arrival night coded `UQ`; later July nights coded `RE`. |
| `135035` | Arrival night coded `UQ`; later nights coded `RE`. |
| `138017` | Early nights coded `RE`; later nights coded `UQ`. |

This explains why a sum of segment-level distinct reservations can exceed the property-level distinct total. For example:

```text
Property-level distinct reservations: 1,815
Sum of segment-level reservations:     1,818
Difference:                                 3
```

The property total is the correct number of unique reservations. Segment totals will reconcile only after a business rule assigns each reservation to one segment, such as the segment on the arrival date. Room nights and revenue may still remain distributed by stay-date segment.

The same behavior can occur for room types when a reservation changes room type during the stay. Room-type room nights remain additive, while room-type reservation counts can overlap.

## Status and cancellation behavior

Known status variants include:

```text
CANCELED
CANCELLED
Cancel
NOSHOW
NO SHOW
CHECKEDOUT
CHECKEDIN
RESERVED
```

Normalize status values with trimming and uppercase before filtering. Queries should account for both US and UK spellings of canceled and for no-show values with or without a space.

### Critical historical behavior

When a reservation is canceled, StayInTouch retains the stay-date rows but changes the production fields from the cancellation point forward:

```text
rms_otb = 0
rev_otb = 0
```

The following fields remain available after cancellation and are therefore important for historical reconstruction:

```text
stay_date
confirmation_number
rate
original_rate
arrival_date
departure_date
cancel_date
book_date
nights
lead_days
```

## Reconstructing STLY OTB without a stored snapshot

The current table is not a complete immutable daily snapshot history. A prior-year OTB position can still be approximated or reconstructed when the reservation row remains present.

A reservation existed at a historical snapshot when:

```sql
book_date <= as_of_date
AND (
  cancel_date IS NULL
  OR cancel_date > as_of_date
)
```

For reservations that later canceled and now have zero `rms_otb` and `rev_otb`:

1. Restore one room night for each eligible stay-date row.
2. Reconstruct nightly room revenue from retained rate fields.
3. Use the lower valid value of `rate` and `original_rate` to reduce the risk of overstating pace revenue.

Recommended conservative rate expression:

```sql
CASE
  WHEN rate IS NULL THEN original_rate
  WHEN original_rate IS NULL THEN rate
  ELSE LEAST(rate, original_rate)
END
```

Approximately 70% of reviewed rows had matching `rate` and `original_rate`. The lower-rate rule is intentionally conservative where they differ.

### Reconstruction limitations

This method can reproduce the historical reservation population more accurately than relying on current `rms_otb` and `rev_otb`, but it is not identical to a true stored daily snapshot when any of the following occurred after the snapshot:

- rate changes not recoverable from `rate` or `original_rate`;
- stay-date, room-type, or segment changes;
- partial cancellations or shortening of stay;
- multi-room reservations where one row does not equal one room night;
- fees, add-ons, taxes, or other revenue changes not represented in the nightly rate;
- source rows removed rather than retained with zero production.

Future ingestion should preserve daily snapshot facts or a reservation-change history so historical OTB does not depend on reconstruction.

## Snapshot and comparison rules

For STLY comparisons:

- TY uses the requested `snap_date`.
- STLY uses `DATE_SUB(snap_date, INTERVAL 1 YEAR)`.
- Closed months use final actual production.
- The current month is labeled `ACTUAL_OTB`.
- Future months are labeled `OTB`.
- Full-year rows combine closed actual months with current and future OTB.

The reporting window currently follows this rule:

| Snapshot date | Report years shown |
| --- | --- |
| January 1 through September 30 | Current calendar year only |
| October 1 through December 31 | Current year plus following year |
| January 1 of the new year | Prior year drops; new current year only |

## Date and duration fields

Use source dates directly when possible:

```sql
lead_days = DATE_DIFF(arrival_date, book_date, DAY)
nights    = DATE_DIFF(departure_date, arrival_date, DAY)
```

`unique_lead_days` and `unique_nights` are populated on selected reservation rows and may be blank on subsequent stay-date rows. They should not be summed across stay-date grain.

For profile reporting, `lead_days` represents the booking lead time of the reservation. A future month can correctly fall entirely into a long-lead bucket when the snapshot date is already more than 91 days before every arrival in that month.

## Deduplication guidance

The pipeline and downstream SQL have used `MAX(rms_otb)` and `MAX(rev_otb)` to suppress duplicated stay-night rows. This is safe only when repeated rows are duplicates of the same economic record.

Before using `MAX`, validate whether repeated rows represent:

- duplicate copies of the same stay night;
- separate rooms in a multi-room reservation;
- separate revenue components;
- separate room-type or segment assignments.

A recommended candidate key for duplicate testing is:

```text
confirmation_number
stay_date
roomtype
metric code when reporting by a changing dimension
```

Do not use a changing dimension in the property-total deduplication key unless the intent is to preserve multiple dimension assignments.

## Validation controls

The pipeline contains a standing January 2026 success criterion:

| Filter | Expected value |
| --- | ---: |
| Stay dates | January 1–31, 2026 |
| Status | `CHECKEDOUT` |
| `SUM(rms_otb)` | 2,235 |
| `SUM(rev_otb)` | 175,872 |

This test is intended to detect row loss, duplicated production, or header and mapping changes as the file moves through the pipeline.

Additional recommended controls:

1. Compare row counts before and after each left join.
2. Report unmatched PMS-to-CRS confirmation numbers.
3. Compare `SUM(rms_otb)` and `SUM(rev_otb)` at every pipeline step.
4. Count duplicate candidate stay-night keys.
5. Count null or `Unassigned` values by segment, source, channel, and subsource.
6. Compare property totals with the sum of dimensional rows and explain overlap from changing assignments.
7. Compare reconstructed STLY rooms and revenue to any retained RMS snapshot extract.
8. Track the share of reconstructed revenue using `rate`, `original_rate`, and the lower-of-two rule.

## Known implementation notes

- Pipeline modules exchange files through `data_upload`, `data_processed`, `data_export`, and `data_failed` folders in Google Drive.
- Source files move to `data_processed` only after successful processing.
- Failed files should move to `data_failed` rather than silently disappearing.
- Header detection should remain anchor-based. Fixed row indexes are not considered reliable across report versions.
- Step 03 references the external `REVREBEL/Metrics-Dataform` column standardizer. Changes to that shared helper can affect this source without a direct edit to the StayInTouch notebooks.
- Step 04 currently reads business mapping tables from a Google Sheet. Those mappings are operational dependencies and should eventually be versioned or mirrored in the Metrics data-model repository.
- `Unassigned` is a valid reporting bucket and must be included in totals.
- A total row must be calculated from the underlying population, not by blindly adding reservation counts from overlapping dimension rows.
