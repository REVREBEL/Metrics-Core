# CoStar Metrics Data Model & Processing Standards

This document defines the structure, processing logic, validation rules, and naming conventions used across the REVREBEL CoStar (STR) analytics pipeline.

The goal is consistency. Not just in naming — but in how the data behaves across ingestion, transformation, reporting, benchmarking, and downstream analytics.

This is the reference layer that defines how CoStar data is organized across the REVREBEL Metrics Library and analytics warehouse. It creates a predictable system where dashboards, pipelines, analysts, and automation workflows interpret the data consistently without requiring custom logic for each use case.

Hospitality data is messy enough already. The structure should not be.

# Core Design Philosophy

CoStar data behaves differently than PMS operational data.

It includes market-level benchmarking, competitive positioning, ranking logic, index calculations, and snapshot-based observations that do not always reconcile directly to operational room-night or revenue production.

Because of that, CoStar datasets are modeled as benchmarking and market-intelligence layers rather than transactional operational fact tables.

This separation preserves:

- operational reporting integrity;
- competitive benchmarking consistency;
- historical market context;
- snapshot-level trend analysis;
- forecasting and demand-modeling accuracy.

The objective is not simply storing data. The objective is preserving meaning.

```text

```

### Base Structure

```text
{metric}

cs_{metric}_ly

industry_{metric}_ly
```

### Percent Change Structure

```text
{metric}_pct_chg

industry_{metric}_pct_chg
```

### Index Structure

```text
{metric}_index
{metric}_index_ly
cs_{metric}_index

```

### Ranking Structure

```text
{metric}_rank

```

This structure keeps related metric families grouped logically and alphabetically while maintaining consistent semantic behavior across the warehouse.

# Competitive Set Logic

Competitive sets are processed independently and preserved as separate benchmarking contexts.

Each competitive set:

- maintains its own historical continuity;
- preserves snapshot-level market behavior;
- supports ranking and index calculations independently;
- maps to a standardized `cs_no`.

Suffix logic:

```text
_1
_2
_3
```

Mapped as:

```text
Set01
Set02
Set03
```

Because competitive sets evolve over time, the model prioritizes traceability over simplification.

Changing the benchmark changes the meaning of the data.

# Property Identification Logic

Property identification follows a structured fallback hierarchy designed to reduce ingestion failures and maintain dataset continuity.

## Primary Method

Extract `property_code` from the filename.

Example:

```text
MSPHEH
```

## Secondary Method

Extract the STR / CoStar identifier (`str_id`).

## Tertiary Method

Match against standardized `property_name`.

Once identified, the property reference becomes the session-level lookup key throughout processing and validation.

# Validation Standards

Every processed row validates against the standardized CoStar reference layer.

Validation includes:

- property alignment;
- competitive-set alignment;
- capacity consistency;
- metadata integrity;
- ranking continuity;
- index calculation consistency.

This validation layer prevents silent reporting drift across dashboards and downstream analytics.

Because bad benchmarking data spreads fast. Usually right before someone screenshots it for ownership.

# Competitive Set Change Handling

## Scenario 1 — Set Reclassification

A hotel reorders an existing competitive-set hierarchy.

Example:

```text
Set03 → Set01
```

This impacts benchmark relationships and index interpretation.

Detection occurs through `cs_id` validation.

## Scenario 2 — Competitive Set Composition Change

The actual members of the competitive set change.

When this occurs:

- a new competitive-set record is created;
- historical continuity is preserved;
- prior benchmarking remains intact;
- reporting logic maintains separation between benchmark versions.

Benchmark history remains historically accurate rather than being retroactively rewritten.

# Week Logic

Week structure follows standard hospitality reporting behavior rather than ISO standards.

- Week starts on Sunday.
- Week 1 contains January 1.
- Each Sunday increments the week number.

This aligns reporting with common STR and hospitality operational standards.

# Warehouse Naming Standards

The CoStar pipeline follows the REVREBEL warehouse naming system.

| Object Type | Standard |
|---|---|
| Fact tables | `metrics_fact_*` |
| Views | `vw_metrics_*` |
| Snapshot tables | `snap_metrics_*` |
| Dimensions | `dim_*` |

Examples:

```text
metrics_fact_costar
vw_metrics_costar_daily
snap_metrics_costar
dim_property
dim_comp_set
```

# Data Pipeline Flow

```text
1. Ingest raw CoStar export
2. Normalize OCC / ADR / RevPAR tabs
3. Flatten into row-based structure
4. Apply competitive set segmentation
5. Expand LY, index, and ranking metrics
6. Validate against reference tables
7. Load into warehouse
```

The pipeline prioritizes:

- reproducibility;
- traceability;
- semantic consistency;
- benchmark integrity;
- reporting stability.

# Common Failure Points

| Issue | Impact |
|---|---|
| Missing `property_code` | Property matching failure |
| Invalid `cs_id` | Benchmark corruption |
| Partial report tabs | Incomplete metric expansion |
| Null percentage changes | Invalid LY calculations |
| Week logic inconsistency | Reporting drift |
| Duplicate comp set rows | Ranking distortion |

These conditions are monitored because hospitality reporting has a remarkable ability to fail quietly and dramatically at the same time.

# Database Naming Standards

All warehouse fields follow standardized lowercase `snake_case`.

The structure prioritizes:

1. metric or entity first;
2. context second;
3. comparison or period third;
4. numeric window last.

Example:

```text
rev_pct_chg_ly_030
```

Not:

```text
revenue_change_last_year_30_day
```

The naming system allows analysts, pipelines, dashboards, and automated documentation to infer meaning directly from the schema without decoding each source table manually.

Clean naming is not cosmetic. It is operational infrastructure.
