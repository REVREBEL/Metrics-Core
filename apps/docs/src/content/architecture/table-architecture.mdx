# Metrics Table Architecture

> **Historical route:** This page formerly combined conceptual architecture with physical table claims. It is retained so existing links continue to work, but it no longer defines the canonical warehouse inventory.

Metrics uses grain-specific analytical structures rather than one generalized fact table. That design direction remains current, but implementation status and exact object names must be read from the maintained subject catalogs and verified against Dataform.

## Durable design principles

The following principles remain part of the Metrics architecture:

- model analytical data by business grain;
- separate snapshot pace, actual production, pickup movement, planning, pricing, and benchmark intelligence;
- preserve additive source measures in fact layers;
- govern reusable derived metrics through semantic definitions, views, reports, or marts;
- keep pickup structures long and narrow where comparison windows would otherwise create schema explosion;
- normalize inconsistent source-system values through governed lookup and mapping layers;
- preserve source lineage and historical meaning rather than rewriting prior benchmark or mapping context.

## Status discipline

An object must not be described as implemented solely because it appeared in the former catalog, an architecture diagram, an application registry, or a fixture.

Use the following labels in maintained documentation:

```text
IMPLEMENTED
PLANNED
COMPATIBILITY
DEPRECATED
UNRESOLVED
```

Dataform is the authority for current warehouse object names, schemas, and dependencies. Repository code is the authority for current application behavior. Linear is the authority for approved product intent and terminology.

## Why the old catalog was retired

The previous version listed objects such as `fact_pace_*`, `fact_actual_*`, `fact_pickup_*`, `fact_metric_observation`, and several marts as though they formed one current physical inventory. Current Dataform instead implements a narrower set that includes staging, snapshot, lookup, mapping, dimension, and view objects, while several broader families remain architecture decisions or future implementation work.

Keeping those categories in one undifferentiated table made conceptual direction look like deployed schema. The canonical pages now separate those two truths cleanly.
