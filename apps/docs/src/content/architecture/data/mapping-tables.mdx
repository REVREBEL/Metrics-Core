# Mapping Tables

Mapping tables preserve source-application values and resolve them into the governed Metrics taxonomy.

The current maintained Dataform implementation source is `REVREBEL/Metrics-Dataform`. App registries and fixtures are scaffolding unless current Dataform creates the physical table.

## Implemented inventory

| Mapping | Status | Grain | Purpose |
|---|---|---|---|
| `metrics_core.map_segment` | **IMPLEMENTED** | One row per property, source application, and source segment code | Commercial and finance segment mapping |
| `metrics_core.map_roomtype` | **COMPATIBILITY** | One row per property, source application, and source room-type/room-class mapping | Embedded room taxonomy mapping |
| `metrics_core.map_source` | **IMPLEMENTED** | One row per property, source application, and source/subsource code | Source, subsource, and channel mapping |
| `metrics_core.map_rate` | **IMPLEMENTED** | One row per property, source application, and source rate code | Full commercial rate classification |

`map_roomtype` is implemented physically, but its embedded taxonomy and `_map` field pattern are compatibility design rather than the preferred pattern for new mappings.

## Source lineage terminology

All implemented source-value mappings use:

```text
source_application_code → lkp_source_application.code
```

`lkp_source_application.source_system_type_code` then connects the application to its broad system category.

Generic registry fields such as `source_system`, `source_value`, `standard_code`, or a universal `source_code` field are not the physical schema. Each mapping table has its own columns and targets.

## Registry-only and architecture-only objects

| Object | Status | Current truth | Required decision or action |
|---|---|---|---|
| `metrics_core.map_hotel` | **PLANNED** | Registry concept only; no current Dataform DDL | Define source-property identity model and relationship to `dim_property` |
| `metrics_core.map_channel` | **UNRESOLVED** | Current channel mapping is `map_source.channel_code` | Decide whether a separate table provides additional value |
| `metrics_core.map_market` | **UNRESOLVED** | No current DDL and no approved canonical market taxonomy | Define market meaning and ownership first |
| `metrics_core.map_agency` | **UNRESOLVED** | `lkp_agency` exists, but no source-value agency mapping exists | Decide whether source agency codes need property/application mapping |
| `metrics_core.map_source_metric` | **UNRESOLVED** | Architecture reference only | Define whether it maps raw report columns, metric codes, or ingestion contracts |

These objects must not appear as live editable warehouse tables until Dataform creates them and their ownership is approved.

## Known integrity risks

- BigQuery does not enforce mapping foreign keys.
- Property references are semantic; current mapping DDL does not declare a physical foreign key to `dim_property`.
- Existing rows created before migration may have null `source_application_code`.
- `map_source.code_reference` requires controlled-value validation.
- `map_roomtype` allows taxonomy drift because standard values are embedded rather than lookup-backed.
- Multi-target `map_rate` rows can contain incomplete or contradictory classifications.

Validation requirements are documented in [Mapping and Lookup Dependencies](/docs/architecture/data/table-dependencies).
