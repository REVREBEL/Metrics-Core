## Source ownership

Use the following authority order when these sources differ:

1. Linear defines product intent, approved terminology, and initiative or project boundaries.
2. Repository code defines the current application implementation.
3. Dataform defines the current warehouse schema, dependencies, mappings, lookups, and assertions.
4. Documentation explains the system but must be reconciled against the sources above.
5. Registries and fixtures are application scaffolding unless current implementation confirms otherwise.

Documentation must distinguish:

```text
IMPLEMENTED
PLANNED
COMPATIBILITY
DEPRECATED
UNRESOLVED
```

This page currently mixes confirmed design decisions with physical-object claims. It will become a concise conceptual overview or be split across the dimension, fact, pickup, and reporting catalogs. Until then, table names shown there require Dataform verification before being described as implemented.

### Keep as historical documentation

- `development/app-migration/01-legacy-application-audit.md`
- historical route, iframe, registry-adapter, or browser DuckDB migration material

Historical pages should receive explicit banners when they are next edited. They are evidence of prior implementation, not the current architecture authority.
