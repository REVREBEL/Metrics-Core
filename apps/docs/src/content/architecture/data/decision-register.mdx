# Data Architecture Decision Register

This is the canonical register for unresolved Metrics data-architecture decisions.

Its purpose is to prevent a missing implementation, registry entry, historical document, or prior ChatGPT recommendation from being presented as approved architecture.

## How to use this register

A decision belongs here when at least one of the following is true:

- Linear has not approved the target behavior;
- current Dataform and repository code implement conflicting contracts;
- multiple technically valid options remain;
- an ownership, migration, versioning, or publication boundary is not settled;
- implementation cannot proceed safely without a product or architecture decision.

A missing table or package is not automatically an unresolved product decision. When product direction is already clear and only implementation remains, the item should be tracked as **PLANNED** in the canonical subject documentation rather than retained here.

## Decision record fields

Each item records:

| Field | Meaning |
|---|---|
| Decision ID | Stable identifier used in issues, reviews, and implementation plans |
| Decision question | The precise question that still requires approval |
| Decision owner | Role or workstream accountable for approval; named ownership may be assigned later |
| Current evidence | What Linear, repository code, Dataform, and docs currently show |
| Current options | Viable choices still under consideration |
| Blocking impact | Work that should not be finalized until the decision is made |
| Affected contracts | Relevant tables, packages, routes, or documentation |
| Related work | Linear issues or canonical docs that own follow-up |

## Decision process

1. Confirm that the question is still unresolved in Linear, repository code, and Dataform.
2. Assign an accountable decision owner.
3. Record viable options and downstream impact.
4. Approve the decision in Linear or another designated product record.
5. Update the canonical subject documentation.
6. Remove the item from this register.
7. Create implementation and migration issues where needed.
8. Add assertions or tests that prevent regression when the decision affects a physical contract.
