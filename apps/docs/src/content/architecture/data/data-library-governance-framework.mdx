# Data Library Governance Framework

The Data Library separates warehouse truth from application workflow state. BigQuery and Dataform own the current governed lookup and mapping values. The Metrics application database owns drafts, change requests, review state, publication state, and audit history.

Browser components never write directly to BigQuery.

## Source ownership

Linear defines the product workflow and governance intent. Dataform defines the physical warehouse schema. The application registry defines which warehouse objects and columns the Data Library may expose or publish. Repository code defines the current workflow implementation.

The application-owned registry is:

```text
apps/app/features/data-library/registry.ts
```

It is a code-owned security allowlist. Client input cannot choose arbitrary datasets, tables, columns, or SQL.

## Registered segment tables

Current Dataform implements these segment objects, among others:

| Category | Physical table | Grain | Logical key | Publication |
|---|---|---|---|---|
| Lookup | `metrics_core.lkp_segment` | One row per governed segment code | `code` | Deferred |
| Mapping | `metrics_core.map_segment` | One row per property, source application, and source segment code | `property_code`, `source_application_code`, `code` | Supported |

For `map_segment`, Dataform currently implements these physical columns:

```text

```

The Data Library registry must remain aligned to Dataform before additional tables are enabled for publication.

## Application workflow persistence

`packages/db` currently owns the application database schema and repository implementation for the Data Library workflow, including:

```text
app_audit_log
app_users
data_library_tables
lookup_table_change_requests
lookup_table_change_request_items
lookup_table_draft_edits
user_roles
```

BigQuery remains the source of truth for published warehouse values. PostgreSQL remains the source of truth for workflow state and governance history.

## Draft and review lifecycle

The implemented change-request lifecycle includes:

```text
draft
→ submitted
→ approved
→ published
```

Alternative terminal or recovery states are:

```text
rejected
withdrawn
conflict
```

Approval and publication are separate permissions. Approval does not grant publication authority.

Review governance continues to enforce the REV-77 contracts, including self-review prohibition, review permissions, withdrawal rules, validation snapshots, and fail-closed database behavior.

## Governed publication path

REV-78 implements controlled publication for `metrics_core.map_segment` only.

The flow is:

```text
Approved change request
→ authenticated publication request
→ exact registry publish-permission check
→ registry table-support check
→ current BigQuery row re-read
→ field-level snapshot comparison
→ atomic BigQuery transaction and MERGE
→ application status transition
→ durable audit event
```

The API boundary is:

```text
POST /api/data-library/publish
```

The canonical feature publication entry point is:

```text
apps/app/features/data-library/publication.ts
```

It exposes the governed orchestration implemented in:

```text
apps/app/features/data-library/publication-service.ts
```

The server-only BigQuery adapter is:

```text
packages/data/src/server/data-library/publication-adapter.ts
```

### Authorization

Publication is allowed only when all of the following are true:

1. the workspace session is authenticated;
2. the change request exists;
3. the registry marks the table publication path as `supported`;
4. the user holds one of the exact registry publication permissions for that table family;
5. the request is in `approved` state, unless it is already `published` and is being safely retried.

The current supported mapping permission is:

```text
data_library.mapping_tables.publish
```

The API also exposes a read-only publication-capability check for UI gating. Server authorization remains authoritative even if a client bypasses the UI.

## Conflict detection

`map_segment.updated_date` is a nullable `DATE` in the current Dataform schema, so it is not used as a row-version token.

REV-78 instead implements optimistic concurrency from the immutable change-request snapshot:

1. the server re-reads the current warehouse row;
2. each field actually being published is compared with the original approved value;
3. if the current value is neither the original value nor the already-requested value, publication stops as a conflict;
4. immediately before mutation, a BigQuery transaction performs the same field-level snapshot assertion;
5. the MERGE executes only if every affected field still matches the approved snapshot.

This closes the race between preflight conflict detection and mutation without overwriting unrelated fields on the same row.

New-row insertion is not part of the current `map_segment` publication contract. A request without an existing original row fails explicitly instead of creating a warehouse row implicitly.

## Atomicity and compensation

The warehouse write for a request is executed through a BigQuery multi-statement transaction. Snapshot assertion and MERGE are therefore one warehouse transaction, preventing silent partial publication inside BigQuery.

PostgreSQL workflow state and BigQuery cannot participate in one cross-system transaction. The compensation strategy is retry reconciliation:

- if BigQuery fails, the request remains `approved` and is retryable;
- if BigQuery succeeds but the application status update fails, a retry re-reads the warehouse values;
- when the requested field values are already present, the warehouse adapter treats them as already applied and performs no duplicate warehouse mutation;
- the application can then reconcile the request and draft statuses to `published`.

Change-request item rows are retained after publication so the immutable governance record is not destroyed.

## Conflict recovery

When a stale-data conflict is detected:

- the change request transitions to `conflict`;
- its associated draft edits return to editable `draft` state;
- the conflict event records the affected row keys and conflicting fields;
- the user should refresh current warehouse values, revise the restored drafts, and submit a new change request.

The conflicted request remains available as historical review evidence.

## Audit and observability

Publication uses the existing `app_audit_log` table. REV-78 records the publication lifecycle events:

```text
publication_started
publication_succeeded
publication_failed
publication_conflict
```

Publication audit metadata includes the request ID, actor, table key, logical row keys, correlation ID, result details, and BigQuery job ID when a warehouse job executes.

Operational failures remain retryable and do not silently advance the request to `published`.

## Supported and deferred behavior

**IMPLEMENTED**

- authenticated Data Library reads;
- registry-driven table and column capabilities;
- application-database-backed drafts;
- change-request submission and review governance;
- server-only BigQuery publication for existing `metrics_core.map_segment` rows;
- exact publish-permission enforcement;
- preflight and transaction-time optimistic conflict enforcement;
- atomic warehouse updates for all rows in the publication operation;
- durable `published` and `conflict` request outcomes;
- draft lifecycle synchronization;
- retry reconciliation and idempotent already-applied detection;
- publication lifecycle audit events with correlation metadata.

**DEFERRED**

- publication for `metrics_core.lkp_segment`;
- publication for other lookup and mapping families until their Dataform schema and registry contracts are verified;
- new-row insertion through the publication path;
- bulk CSV import/export;
- unmapped-values workflow, which belongs to REV-79.
