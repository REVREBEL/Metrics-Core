# Data Library Governance Framework

## Current implementation

The authenticated Metrics workspace route at `/metrics-library` now reads its
lookup and mapping navigation, capability metadata, and column behavior from
the application-owned registry:

```text
apps/app/features/data-library/registry.ts
```

The registry is the authoritative warehouse security allowlist. Linear defines the
live read requirement, while Dataform implements physical tables and columns. A future
`data_library_tables` database record may supplement operational display metadata,
but it must not expose an arbitrary warehouse table that is absent from the code-owned
registry.

The first registered definitions are:

| Category | Physical table | Grain | Logical key |
|---|---|---|---|
| Lookup | `metrics_core.lkp_segment` | One row per standard commercial segment code | `code` |
| Mapping | `metrics_core.map_segment` | One row per property, source application, and source segment code | `property_code`, `source_application_code`, `code` |

Live rows are queried through the server-only warehouse data adapter in `@repo/data/server/data-library`.
Browser components do not receive warehouse credentials, construct raw SQL queries, or access BigQuery directly.

The application database does not introduce warehouse identifiers. Durable draft,
change-request, role-backed permission assignment, and audit behavior remain
blocked until the existing deployed schema and repository-owned service contracts
are restored or supplied.

## Validation and conflicts

Registry metadata identifies required, editable, read-only, filterable, sortable,
searchable, and lookup-dependent fields. Full validation runs at the server
boundary before queries are built and executed.

Current Dataform defines `updated_date DATE` on both registered tables. The
segment seed initializes it as null, and no non-null row version or timestamp
constraint is implemented. Optimistic conflict detection is therefore
**UNRESOLVED**. The UI and service must not claim conflict safety until a
reliable concurrency contract is approved.

## Workflow Security & Lifecycle Governance [REV-77]

The change-request governance framework implements a secure, state-machine-controlled review and audit workflow designed to prevent self-review and enforce separation of duties.

### 1. State-Machine Lifecycle Transitions
Change requests and associated draft edits transition through a deterministic lifecycle:
* **Draft to Submitted**: Submitting selected draft edits transitions their state to `"submitted"`. Attempts to submit edits that are already submitted, approved, or belong to another user will fail closed.
* **Review Approval**: Approving a request transitions its state to `"approved"` and locks down the draft edits to prevent further modification.
* **Review Rejection**: Rejecting a request transitions its state to `"rejected"` and returns the draft edits back to `"draft"`, enabling the submitter to refine and resubmit them.
* **Withdrawal**: Withdrawing a request transitions its state to `"withdrawn"` and returns the draft edits back to `"draft"`.

### 2. Multi-Role Authorization & Capability Mapping
Access control is enforced at every layer of the workflow:
* **Submit Change Request**: Requires `data_library.change_requests.submit` or `data_library.change_requests.admin`. Title (3-100 characters) and Description (up to 500 characters) length bounds are strictly enforced.
* **View Queue**: Submitter/Viewer roles (`data_library.change_requests.submit` or `view_own`) are strictly scoped to only view requests they submitted. Reviewer/Admin roles can view the entire queue.
* **Direct Get Details**: Requires verification of explicit permissions (`view_own`, `submit`, `review/decide`, `admin`) **before** checking ownership. A revoked user with zero permissions cannot fetch their request details even if they are the original submitter.
* **Review Approval/Rejection**: Requires `data_library.change_requests.decide` or `admin`. Rejection notes must be at least 3 characters and up to 2,000 characters. **Self-review is strictly prohibited**: if `submitterId === reviewerId`, the action fails closed with a `FORBIDDEN` error.
* **Withdrawal**: 
  * Administrators can withdraw any submitted request.
  * Submitters with `submit` or `view_own` permissions can withdraw only their own requests.
  * Reviewers without admin status cannot withdraw requests submitted by others.

### 3. Fail-Closed Database Failures
To ensure production environments fail closed if dependencies are misconfigured:
* Resolving database-backed repositories outside active database connections throws a `DatabaseConfigurationError`.
* All change-request service methods resolve the repository inside isolated `try/catch` blocks.
* Missing database configurations (`DATABASE_URL` is undefined) are safely captured and returned as structured, non-retryable `INTERNAL_ERROR` service responses with a clear message, ensuring the application blocks unauthorized access gracefully.
